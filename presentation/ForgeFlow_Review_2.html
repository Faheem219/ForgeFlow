Introduction

ForgeFlow — An AI-Native, Human-in-the-Loop Platform for the Automated Web SDLC

Screenshots or a spec in a tested, deployed website out.

PWA with an embedded browser IDE — Monaco editor and terminal built in; generated code stays visible and editable, not a black box.

No stage is mandatory. Enter anywhere, refine anything, skip anything, jump back at will — non-linearity is an invariant of the design.

Core technical contribution: a bounded, diff-aware self-healing repair loop — verification that terminates instead of thrashing.

Fixed generated stack — React + Express + MongoDB — gives higher first-pass success and makes rigorous verification tractable.

Research Gaps (2/3)

Repair Has Diminishing Returns — and Generated Tests Decay When Code Changes

The repair loop has an economics

The vast majority of the benefit of a repair loop is gained in the first one to three iterations — later iterations mostly consume tokens for little further gain.

Kiecker et al. [9] · Arimbur [10]
Security cost [5]

Iterating self-improvement is not merely low-yield past a point — repeated “make it more secure” rounds can monotonically weaken security.

Build-code quality [4]

A 2026 mining study finds agents systematically introduce maintainability and security smells into generated build code.

Traceability [20]

TraceLLM recovers requirement-to-artifact links after the fact; ForgeFlow builds the link in by construction via criterion_id.

Design consequence: an unbounded repair loop is a cost sink and a safety risk. Our iteration cap (default 5, just above the 1–3 knee), regression guard, stall guard and budget guard are a response to this literature.

The strongest 2026 evidence — LLM tests under software evolution [11]

8 LLMs22,374 program variants≈346M tokens
>99%

of the failing tests pass on the original program — “residual alignment”: the model tests the code it remembers, not the code it was given.

“Computing a code diff and explicitly highlighting the modified regions could help guide the model’s attention.”

— the authors’ recommended fix [11]

This is precisely ForgeFlow’s diff-aware minimal repair context — designed and built, then independently corroborated by this study.

A March-2026 study, independently, tells you to do the exact thing we built — and to stop early.

Conclusion

Verification, Not Generation, Is the Frontier — and It Is Built

The industry has an adoption–trust inversion: adoption fell 84%→76% year on year [3] while trust in AI accuracy fell to 29% [3] — and 43% of AI code still fails in production after QA [25].

ForgeFlow addresses the failure that matters — verification, not generation — with a bounded, diff-aware, human-escalating repair loop.

A complete first prototype is implemented: 53 phases, 12 epics, ≈41,000 lines of production code and 1,491 automated tests — screenshots → deployed and re-validated URL.

The design is independently corroborated: a March-2026 study of 22,374 program variants recommends diff-highlighted repair context after finding >99% residual alignment in LLM-generated tests [11].

The differentiator is defensible: research verifies without deploying; industry deploys without verifying. ForgeFlow closes both loops — and stops.

New this cycle: deploy → live-validate testing is complete, and the platform now hosts the full generated application — frontend and backend — on a single provider (Vercel), removing the ordered cross-provider deployment failure mode identified in [6].

Next: the three-arm evaluation (Section VIII of the paper), adversarial gap-finding, and production-readiness hardening.

“

Anyone can make an AI write an app. The hard part is knowing when it’s actually finished — and that is what we built.
