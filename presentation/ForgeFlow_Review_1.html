Introduction

ForgeFlow — An AI-Native, Human-in-the-Loop Platform for the Automated Web SDLC

Screenshots or a spec in a tested, deployed website out.

PWA with an embedded browser IDE — Monaco editor and terminal built in; generated code stays visible and editable, not a black box.

No stage is mandatory. Enter anywhere, refine anything, skip anything, jump back at will — non-linearity is an invariant of the design.

Core technical contribution: a bounded, diff-aware self-healing repair loop — verification that terminates instead of thrashing.

Fixed generated stack — React + Express + MongoDB — gives higher first-pass success and makes rigorous verification tractable.

“

Existing tools generate apps. ForgeFlow generates apps it can prove work — and then proves it again on the live URL.

Updated Literature Survey (2/3)

Self-Repair Is Not a Silver Bullet — and Humans Stay in the Loop

Self-repair is not free

Once repair cost is accounted for, gains are “often modest, vary a lot … and are sometimes not present at all” — self-repair is bottlenecked by the model’s own feedback quality.

Olausson et al., ICLR 2024 [14]
Human gap [14]

Even for the strongest models, self-repair lags far behind human-level debugging.

Self-Debugging [15]

Improves outcomes, but depends critically on the quality of execution feedback.

Direct design consequence: an unbounded repair loop is a cost sink, not a feature. ForgeFlow’s retry caps, no-progress detection and escalation are a response to this literature — not an arbitrary limit.

Human-in-the-loop is the deployed industrial pattern

HULA [16]

Deployed inside Atlassian Jira — engineers keep control of planning and code at every step.

HULA follow-up [17]

Flags the two open challenges: the high cost of correctness testing and the variability of LLM-based evaluation.

Test generation at scale — proven, but narrow

Schäfer et al. [18]

IEEE TSE empirical evaluation of LLM-based automated unit-test generation.

Meta (FSE) [19]

Industrial deployment of automated unit-test improvement at scale.

ICSE 2026 [22]

Program-analysis-guided iterative test generation — hybrid static/LLM pipelines.

Updated Literature Survey (2/3 — contd.)

The Strongest 2026 Evidence: LLM Tests Degrade Exactly When Code Changes

Haroon, Khan & Gulzar — arXiv, Mar 2026 [20] 8 LLMs22,374 program variants≈346M tokens baseline: 79.3% line / 76.1% branch coverage, fully passing suites

Even semantic-preserving refactors drop the pass rate to 78.9%; test-suite match rate falls to 18.1% — models discard higher-coverage tests for weaker ones.

>99%

of the failing tests pass on the original program — “residual alignment”: the model tests the code it remembers, not the code it was given.

“Computing a code diff and explicitly highlighting the modified regions could help guide the model’s attention.”

— the authors’ recommended fix [20]

This is precisely ForgeFlow’s diff-aware minimal repair context — designed and built, independently corroborated by this study.

Conclusion

Verification, Not Generation, Is the Frontier — and It Is Built

The industry has an adoption–trust inversion: 84% adoption [1] against 29% trust [1] — and 43% of AI code still failing in production after QA [2].

ForgeFlow addresses the failure that matters — verification, not generation — with a bounded, diff-aware, human-escalating repair loop.

A complete first prototype is implemented: 50 phases, 11 epics — screenshots → deployed and re-validated URL.

The design is independently corroborated: a March-2026 study of 22,374 program variants recommends diff-highlighted repair context after finding >99% residual alignment in LLM-generated tests [20].

The differentiator is defensible: research verifies without deploying; industry deploys without verifying. ForgeFlow closes both loops — and stops.

Next: hardening, adversarial gap-finding, scaled evaluation with ablations, and production-readiness.

“

Anyone can make an AI write an app. The hard part is knowing when it’s actually finished — and that is what we built.
