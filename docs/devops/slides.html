Deployment architecture

Two runtimes, for one specific reason

ForgeFlow runs untrusted generated code in a Docker container per project, and routes previews to those containers by name over Docker's embedded DNS. That single fact decides the whole topology.

Why not Kubernetes for production

Mounting the Docker socket into a pod solves sandbox creation. It does not solve sandbox routing — a pod on the CNI cannot resolve forgeflow-sb-<id>. Fixing that means rewriting preview discovery to use IP addresses: a change to how the application works, not how it is deployed.

So the split is deliberate

Compose serves production with every stage functional. k3s carries the orchestration deliverable. A failed demo can never take production down.

One API replica, on purpose

The control plane keeps WebSocket subscribers, the realtime replay ring and its rate-limiter counters in process memory. --workers 2 would silently halve the limits and drop half the subscribers — a bug, not a speedup.

Pipeline flow

CI proves it. CD ships it — or puts it back.

workflow_run, not push

A push-triggered deploy races CI — it can be serving traffic while the test that would have failed it is still running.

Immutable SHA tags

If the VM tracked latest, rolling back after a bad deploy would roll back to the bad deploy.

Health is polled, not slept on

The deploy watches the image's own HEALTHCHECK — the same signal Docker uses — and treats the timeout as failure.

Two health checks

Loopback proves the container is up. The public HTTPS check proves a user can reach it — catching a healthy container behind a broken proxy.

Challenges

Every config parsed correctly while being wrong

The WebSocket that isn't

ForgeFlow's realtime hub is a WebSocket. A standard nginx proxy_pass block does not forward the upgrade handshake — and the failure is silent. Every REST call works, nothing appears in any error log, and the only symptom is that live build and test streaming never connects.

Tested both ways against a real nginx, with the same request:

With proxy_http_version 1.1 + Upgrade + Connection 101 Switching Protocols
Identical config, those three lines removed 200 OK

Proving the headers work is half the evidence. Removing them and watching the handshake degrade is what proves they are load-bearing rather than cargo-culted.

Oracle Cloud has two firewalls

Oracle's Ubuntu images ship an iptables ruleset whose INPUT chain ends in a blanket REJECT. ufw writes to a different chain — so ufw allow 443 succeeds, ufw status shows the port open, and packets are still dropped.

The playbook removes those rules by specification, not by index — deleting by index while the chain shifts removes the wrong rule, and the wrong rule is the one keeping SSH open — then persists with netfilter-persistent save, without which they return on reboot.

The OCI Security List is a genuinely separate firewall that no playbook can reach.

Caddy label indexing

Host labels count right-to-left, so the dev config's hardcoded index silently resolves to the TLD on a real domain. Re-anchored the regex on the left.

Caddy bound :443

With auto_https off, a bare hostname still listens on 443 — so it never saw the plain HTTP nginx forwards. Fixed by pinning http://.

Metric cardinality

A raw path label mints a series per project, and a scanner mints one per probe. The label is the route template; unmatched requests collapse to <unmatched>.

A panel blank when healthy

sum(rate(...5xx)) returns an empty vector with no errors, and empty ÷ anything is empty — so a healthy service read "No data". Fixed with or vector(0).

arm64 under emulation

Runners are amd64, the VM is aarch64; an amd64-only image pulls fine then dies with exec format error. QEMU + buildx, with a registry cache because emulation dominates build time.

Lessons learned

Validate by execution, not by inspection

Spinning up a throwaway k3s cluster and a real Prometheus cost about an hour — and found five genuine bugs that every linter had passed.

The Caddy label bug, the :443 bind, the missing WebSocket headers, the blank error-rate panel, the cAdvisor relabel collision. All syntactically valid. All obvious within seconds of sending a real request.

“Zero downtime” is a measurement, not an adjective

A rolling update that looks fine proves nothing. Counting 807 requests with 0 failures across an update, a failed release and a rollback is a claim; watching pods change colour is an anecdote.

A deploy command that returns is not a deploy that worked

kubectl set image and compose up -d both return before anything is serving. Every deploy path here waits on a real health signal — and that timeout is the only thing that makes automatic rollback possible.

Make the dangerous thing loud

Regenerating FERNET_KEY is unrecoverable — it decrypts the credential vault. The playbook reads the existing value back rather than re-templating it. Idempotency here is the difference between a re-run and data loss.

Automation that shares a box must be a good neighbour

The VM already runs another project. The nginx role writes exactly one new file, never touches nginx.conf, warns on a server_name collision, validates before reloading, and reloads rather than restarts.
