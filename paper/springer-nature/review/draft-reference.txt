Abstract—Creating a web application is almost trivial with large-language-model coding assistants and "prompt-to-app" builders, but verifying it is challenging. Empirical evidence from recent years demonstrates that AI-generated artifacts are systematically flawed in maintainability and security, that repeatedly asking the model to refine its own code can lead to a decrease in its security, that the success rate of the first deployment of the infrastructure generated by the model is less than a third, and that unbounded repair loops lead to the consumption of budget long after the marginal gain has been lost. This paper introduces ForgeFlow, an AI-native, human-in-the-loop Progressive Web Application that takes an idea for a web-app (provided as screenshots or as a structured specification) and carries it through the process of requirements capture, UI design, generation of full stack code, generation of requirements-based tests, bounded, diff-aware self-healing repair loop, infrastructure-aware dual-mode cloud deployment, and validation against the live URL. ForgeFlow is different from research agents and commercial builders through two design commitments. First, the repair loop is explicitly terminating: it is given a small context, just the failing tests, the sources on which the tests are exercised, and the Git diff since the last passing run, and the loop stops when the first of a regression guard, a no-progress guard, an iteration cap or a budget cap is reached, and the human is handed an auditable "here is where I am stuck" summary. Second, non-linearity is not a UI affordance; each stage preserves its own state, there is no requirement that any particular stage be present, and only two of the stages are ordered. We describe the architecture, the traceability chain that connects acceptance criteria to executable tests and back to repair context, and a working prototype of about 54 000 lines of production code and 2 323 automated tests. A two-level evaluation with validated graders, 95% confidence intervals and per-item latency shows that, on HumanEval, MBPP and HumanEval-TS run through ForgeFlow’s own model interface, bounded repair raised pass@1 from 97.0%, 96.1% and 97.5% to 99.4%, 98.8% and 98.7%, converting 13 of 19 first-attempt failures within two attempts (exact McNemar p < 0.001) for 5.7% more model calls, and stopped itself on the other six before reaching the iteration cap. On the first two of ten full-stack benchmark applications, 12 of 16 acceptance criteria were met; every unmet criterion was a browser end-to-end test outside the repair context, so the loop escalated instead of guessing. We report this failure mode, and the ablations not yet run, as explicit limitations.

Keywords—AI-native software engineering, large language model agents, automated program repair, self-healing software, human-in-the-loop systems, automated test generation, requirements traceability, DevOps automation, progressive web application, empirical evaluation

I.  INTRODUCTION

There are now a number of large language models that are used throughout the entire software lifecycle, with a recent survey systemizing 926 studies on 112 software engineering tasks throughout 5 phases of the SE workflow [1]. Concurrently, a user-centric category has grown up in which a natural-language query is directly converted to a deployable application, a survey of vibe coding in 2025 identifies and formalizes existing practice, including planning-driven and test-driven forms of vibe coding [2]. Adoption is no longer fringe: The 2025 Stack Overflow Developer Survey shows that the share of developers using or intending to use AI tooling has risen from about 76% to 84% year on year, while trust in the accuracy of AI output has declined [3].

This is not a perception gap, it's a measurable one in the artifacts themselves. In 2026, researchers conducted a study on the mining of build code generated by AI across four widely used build systems (Maven, Gradle, CMake and Make) and identified a set of maintainability and security smells that agents systematically introduced in the build code [4]. A more direct application to any system that is able to repair its own output is a controlled study of repeatedly asking a model to generate more secure code, which showed that the security properties of the code could monotonically weaken with repeated iterations rather than monotonically strengthen, and an unbounded "keep fixing it" loop is not just a waste but it is actually dangerous [5].

The weakness is most apparent during deployment. The success rates for two frontier models were 30.2 % and 26.8 % to deploy them successfully the first time, when tested on a benchmark of real tasks [6]. Generation and deployment are therefore not the same issue and passing a local test suite is not proof of behaviour.

The second axis of failure is control. A large scale study of 20 574 real-world coding-agent sessions identifies pervasive developer–agent misalignment, where the agent's actions differ from what the developer intended [7]. A complementary study of professional practice revealed that experienced developers are not giving control over agents to them, but constantly restraining, monitoring and directing them [8]. It is therefore a requirement for any system that is intended to be trusted to be inspectable, revisitable and skippable: even by the users who can't read the code it generates.

Last but not least, the repair loop has an economics. A 2026 empirical study of LLM-based repair loops investigates the number of iterations that are worth performing, and a follow-up study over model sizes and benchmarks reveals that the vast majority of the benefits of the repair loops are gained within 1–3 iterations, with subsequent iterations consuming tokens for the most part [9, 10]. In isolation, LLM test generation fails badly when the program under test changes, with most of the new test failures still passing on the original program (the model tests the code it remembers, not the code it was provided) and the authors explicitly recommend computing a code diff and marking the changes to guide the model's attention [11].

These five findings are the impetus to ForgeFlow. Its contributions are:

A bounded, diff-aware self-healing repair loop that is only fed failing tests, the sources those tests exercise, the Git diff since the last passing run, and the acceptance-criterion text; and that terminates on the first of a regression guard, a no-progress guard, an iteration cap or a budget cap.

Escalation to first class terminal state. Non-convergence is a normal outcome that is recorded and provides the human with a structured summary of the failed tests, patches tried and convergence metrics, not an error or a silent loop.

Non-linearity as a principle of the architecture. The six stages are independent and a project can be entered at any stage, any stage can be skipped, refinement means that work downstream is stale but not deleted. Only deploy ⇐ build and validate ⇐ deploy is enforced.

A requirement-to-repair traceability chain consisting of a single criterion identifier that passes through the following steps: User authored acceptance criterion, test generation, test execution, failure analysis, repair context.

Infrastructure-aware, dual-mode deployment and post-deployment validation, where the generated suite is re-executed against the live URL and live failures re-enter the same bounded repair loop.

A two-level evaluation with validated graders, 95% confidence intervals, a paired significance test, latency and cost measurement, and a failure analysis: four industry benchmarks run through ForgeFlow’s own model interface and repair policy, and full-pipeline runs on a seeded corpus of application specifications.

ForgeFlow does not propose a new model, test generator, sandbox or hosting platform: LLMs, Vitest, Jest, Playwright, Docker isolation and Vercel/Atlas deployment are established components that it uses as they are. Its contribution is the control layer around them — the termination guards and their precedence, the diff-since-last-green context policy, escalation as a terminal state, the criterion-identifier chain and the invariants that let any stage be skipped — and their integration into one lifecycle. II. RELATED WORK

Review method. This is a targeted, structured review, not a full systematic review; its protocol is stated so that it can be repeated. Window: January 2025 to July 2026, when agentic coding tools reached mainstream use [3]. Sources: IEEE Xplore, the ACM Digital Library, SpringerLink, the ACL Anthology and arXiv (cs.SE, cs.AI), searched with “large language model” or “agent” combined with each thread’s terms (program repair and self-repair; test generation and traceability; human-in-the-loop; design-to-code; infrastructure deployment and sandboxing). Inclusion: an empirical study, benchmark or system evaluation whose finding bears directly on a design decision in an AI delivery pipeline. Exclusion: position papers without an evaluation, and vendor material other than the developer survey used for adoption figures. Peer-reviewed versions were preferred; arXiv preprints were kept only where they are the most recent evidence on a thread and are marked as such. Each work was coded by thread (A–E below) and by the design decision it informs (Section IX-A). Screening counts were not recorded, so the review is representative rather than exhaustive.

A. Agentic Code Generation and Issue Resolution:

Agentic software issue resolution has developed into a subfield, which can be categorized into benchmarks, techniques and empirical studies, based on over 150 main studies, in a 2025 survey [12]. A major counter-current is Agentless, which showed that a simple, structured three-phase pipeline could perform at least as well as complex autonomous agents on issue resolution and use significantly less budget [13]; a result that suggests that simple, structured scaffolding can beat unconstrained agency. Meanwhile, fully autonomous repair agents like RepairAgent that can dynamically plan and invoke repair tools using an LLM have been demonstrated to successfully repair real-world defects at competitive rates [14]. The Agentless lesson is the lesson ForgeFlow uses, as opposed to the autonomous-agent lesson, where the pipeline is fixed and deterministic, an opinionated project skeleton is instantiated by file copy instead of generated, and the model is invoked only when actual synthesis is needed.

B. Program Repair and the Economics of Iteration:

The results of these fine-tuning studies, published in IEEE TSE, prove that the quality of the repairs generated by an LLM is highly dependent on the way the repair task is formulated and the context provided [15]. The 2026 repair-loop literature brings the economic dimension to the earlier literature missing: how many attempts are worth it [9] and where is the marginal return at the end [10] across model scales and benchmarks. The security-degradation analysis of iterative generation provides the safety argument for the same conclusion, that later generations are not just low-yield, but potentially harmful [5]. These loops are measured by existing work; they are not normally designed into a delivery system. ForgeFlow implements iteration caps, stall detection, a regression guard and a budget guard as first-class, configurable, auditable controller state. 

C. Test Generation and Requirements Traceability:

Automated Test Generation using LLMs is well-defined. A large-scale study in Empirical Software Engineering was performed to evaluate the effectiveness of prompt-engineering strategies for producing class-level unit-tests over hundreds of thousands of produced tests [16] and an ISSTA study fine-tuned 37 models across three different unit-testing scenarios and five benchmarks [17]. Feature-driven end-to-end test generation [18] and hybrid program-analysis-guided iterative generation [19] are closer to ForgeFlow's goal: generate executable E2E tests from application features and enhance the validity of generated suites. On the requirements side, prompt-engineered LLM traceability has been demonstrated to be able to effectively recover requirement-to-artifact links [20]. The critical negative result is [11] generated suites lose validity when the code changes, and the recommended mitigation is a highlighted diff. The minimal repair context is exactly a diff-highlighted context and the context was designed and implemented for the same reason. 

D. Human-in-the-Loop Control 

It's not about autonomy, it's about human-in-the-loop, which is what is used in industry. HULA, deployed within Atlassian Jira, maintains engineers' control over both the coding plan and the resulting code, and the follow-up reports on meaningful reductions in development effort [21] with the cost of correctness testing and the variability of LLM-based evaluation as the main open challenges [22]. The professionals' deliberate control over the process, not delegating everything, is confirmed in independent observational work; what happens when the professionals are unable to do this is quantified in large-scale session analysis [7, 8]. ForgeFlow abstracts this from "review the plan and the patch" to "enter, refine, skip or revisit any stage of the lifecycle", and it considers the cost of correctness testing mentioned in [22] as a first-class engineering constraint, by model routing and budget caps. 

E. Multimodal Design-to-Code 

Design2Code benchmarks multimodal code generation from 484 real web pages, and demonstrates that models are still behind when it comes to visual element recall and layout fidelity [23]. But ForgeFlow is not just a one-shot conversion whose output is blindly fed downstream, it's a pluggable, human-refinable stage that has versioned artifacts and an explicit skip path.

III. SYSTEM DESIGN

[]

1.  ForgeFlow system architecture: the presentation, control and execution planes, and the external provider boundary. Untrusted generated code executes only inside the per-project sandbox, which has no host network.

Design Principles

P1: Verification over generation. The defensible contribution is knowing when the system is finished, not how quickly it emits code.

P2: One fixed generated-app stack. Every generated application is React (Vite + TypeScript) on the frontend, Node/Express (TypeScript) on the backend, and MongoDB via Mongoose, tested with Vitest, Jest + supertest, and Playwright. Constraining the target raises first-pass generation success, reduces the number of repair iterations required, and makes rigorous verification tractable within a student project's budget. It also lets a hand-written 53-file skeleton be copied rather than generated, which removes scaffolding tokens entirely — the deterministic-scaffolding lesson of [13].

P3: Cost discipline as an architectural concern. Model roles are separated, and model identifiers are configuration, not identity: a code-generation role (default claude-sonnet-5) for synthesis, repair and test generation, and a cheap routing role (default claude-haiku-4-5) for classification, summarisation and the freeform-description-to-feature-list draft. Every call records token usage against the project, and per-project and global budget caps halt work with an actionable message. This is a direct engineering answer to the "high cost of correctness testing" challenge named in [22]. A provider abstraction additionally allows any OpenAI-compatible endpoint to be substituted without touching agent, tool or cost code. The evaluation in Section VIII uses this path, with z-ai/glm-5.3-flash in both roles.

P4: Never overwrite; always version. Artifacts — designs, code changes, requirements, test suites, test runs, repair attempts, deployments, infrastructure plans — are versioned, never replaced, which is what makes "revisit and refine" safe.

P5: Untrusted code runs only in sandboxes. The control plane never executes generated code. Each project receives a Docker container running as a non-root user with no host network, dropped capabilities, and CPU, memory and PID limits, reaped when idle. Recent work on securing test environments for untrusted code documents how wide the escape surface of naïvely configured execution environments actually is [24]; ForgeFlow treats the sandbox boundary, not the model's good behaviour, as the security control.

P6: Non-linearity is an invariant, not a feature.

Architecture

The structure of ForgeFlow is divided into three planes and an external provider boundary (Fig. 1). The control plane is a FastAPI (Python 3.11) service that has Pydantic v2 schemas at all boundaries and Motor/Beanie on top of MongoDB. It includes authentication, project lifecycle and state of the project stages, the conductor, the six stage handlers, the agent layer, the sandbox manager, the deployment orchestrator, the encrypted credential vault, the evaluation harness, and a WebSocket hub. For every project a separate application database is created, and there is a forgeflow_meta database for control plane metadata.

Each execution plane consists of a single Docker container that contains the workspace backed by Git, the generated application, the reverse-proxied preview of the application's development servers, and the test runners. The diff in Section V is not just a side-benefit of Git backing: It is what makes it computable.

The presentation plane is a PWA (Progressive Web App) installable using React 18: dashboard, a clickable stage navigator (workspace shell), a Monaco-based IDE that renders code as the agent writes it, an xterm.js terminal bridged to the sandbox shell, a live preview pane, a test-and-repair pane, a React Flow deployment topology, and a project data browser.

All work of long duration is event driven. A typed event has {event, project_id, stage, payload, seq}; clients subscribe per project and resume from the previous seq after disconnect, so there is no loss of an in-flight generation/repair loop when the page is reloaded.

The Non-Linear Stage Model

[]

2.  The non-linear stage model. Dashed edges are not required (enter-anywhere and skip); the two bold edges are the only required orderings; artifacts in downstream edges are not deleted, but a staleness cascade is propagated.

The flow of the product is requirements – design – build – test – deploy – validate. This order drives the navigator, the default entry stage and the staleness cascade and gates nothing.
One StageState is maintained for each project at each stage, and has statuses of {empty, in_progress, awaiting_user, complete, skipped, stale}. Three behaviours follow:

Enter anywhere. If a user has an existing design, he/she can begin at build, and if he/she has an existing workspace, he/she can begin at test.

Skip. Any stage can be skipped and each downstream handler must be able to accept missing artifacts from upstream handlers. No requirements are present when generating a test: warnings are issued and the test generation offers to capture the requirements or to infer a minimal set; it does not refuse.

Jump back and improve. If a stage is completed, re-entering it starts a new conversation round, outputs are new versions of artifacts, and any downstream stages are marked stale (not deleted) and remain inspectable and re-runnable.

Transition legality is the responsibility of the conductor, not the UI. It takes in an intent {message, target_stage, action ∈ refine | proceed | skip} and passes it to a stage handler, stores messages and artifacts, and sends out events. Centralising legality in one component is what keeps non-linearity a property of the system, and not one screen.

Requirements precede design in the product order because a UI should not be designed before it is known what the application must do; when a specification exists, it is passed to the design provider’s prompt as additional context. This is a soft nudge in the interface, not a gate, consistent with the human-control evidence in [7], [8].

IV. REQUIREMENTS-DRIVEN VERIFICATION

[]

3.  The traceability chain. A user written acceptance criterion is passed through a single criterion_id which are used to generate and execute tests, as well as to analyse failures and repair them, and are reattached to the requirement text when attempting a patch.

Structured Capture

A RequirementSpec contains a list of features, all of which have a name, description, set of inputs, expected behaviours, and acceptance criteria. Capture is not free prose, but is deliberately structured to get deterministic, evaluable test generation from it. They have two entry points: one guided and the other is an AI draft where a freeform description is translated into a proposed feature list by the routing model. The draft is never auto-saved, it is presented for editing and for following the human-control principle.

Compilation to Executable Tests

The test-generation agent assigns each acceptance criterion to one or more executable test, each test being assigned with the identifier of the criterion that it tests: Vitest and Testing Library for frontend units, Jest with supertest for backend units, Playwright for end-to-end behaviour exercised against the sandbox preview. This is very similar to the E2E derivation in [18] with the exception that an explicit identifier is added for traceability to persist in execution.

Execution and Normalisation

Suites run in the project sandbox. The output of the JUnit and JSON reporters are normalised to a per-test record {status, assertion, stack, files_referenced, criterion_id}. Three reasons for normalisation:

1)  The repair context in Section V is compiled deterministically from it.

2)  A criterion that fails will not be included in an aggregate "tests passed" but will be reported as unmet.

3)  The shape produced by the live validation run in Section VI is the same, so that the repair path is framework agnostic.

V.  THE BOUNDED, DIFF-AWARE SELF-HEALING REPAIR LOOP

[]

4.  The bounded self-healing repair loop: minimal context assembly, targeted patching, re-execution, termination guards in order of precedence, and escalation as terminal state.

This is the core contribution. It's given at least one TestRun that fails, the current workspace, and the requirements that the failing tests represent.

Minimal, Diff-Aware Repair Context

The context assembly is deterministic, model free and is exhaustively testable. It allows only four things to be admitted:

1)  Only the failing tests are listed here: name, framework, assertion, stack, referenced source files, and criterion_id.

2)  Only sources for those tests that fail: the failing test's source and files listed in the failing test's stack, widened along the failing test’s import graph by a breadth-first walk bounded at depth 3 and 24 files. Package imports never resolve, so dependencies cannot enter the context, and the agent may request at most three further non-test files per attempt.

3)  The difference between the current and last-passed line. This reference is moved: it is moved forward on each green run, not on the last commit, so the diff says “what changed since it worked”, rather than “what changed in the last commit.” After observing that tests generated by this approach are not robust with respect to evolution and that models do not attend to presented code, this is the mechanism that [11] recommends.

4)  The requirement snippets for the failing criteria and a criterion_id, to allow the agent to repair against the acceptance text instead of just the assertion.

By construction, everything else is excluded (the rest of the repository, passing the tests, untouched modules). This result is capped (24 000 characters total, 8 000 per file, 8 000 of diff, all run-time-configurable); parts that are too large are simply dropped, and the number of times they are dropped is recorded, so a context which is too large is never silently lossy.

Targeted Patch and Re-execution

The repair agent only gets this context, and a hard constraint to repair the failing behaviour without breaking the passing tests. The patch is then put into the sandbox workspace and committed. The affected suite is rerun on the fast path and then rerun on the full path to check for regressions the fast path may not have discovered.

The Loop Controller (Bounded Repair Controller)

Four guards terminate the loop, evaluated in a deliberate precedence order (defaults in parentheses; all admin-tunable):

-   Regression guard (2). Trips on the second attempt that breaks a previously passing test. It is evaluated first because “my patches keep breaking working code” is a more precise and more actionable diagnosis than “no progress”; a single regression is tolerated because a legitimate patch can briefly break one test. An attempt that broke something and fixed nothing is reverted, so the loop never hands back an application worse than it found.

-   Stall guard (2). Trips when the failing-test set has not shrunk for stall_threshold consecutive iterations; a set that stays the same size counts as no progress, and any shrink resets the counter.

-   Iteration cap (5). Checked before each model call. The default sits just above the one-to-three-iteration range in which the literature finds most of the achievable gain [9], [10], because further iterations are unproductive and can degrade security [5]; Section VIII-C tests this choice.

-   Budget, cancellation and blocked attempts. The loop also ends when the budget cap is exhausted, the user cancels, the agent reports that nothing in its context is safe to patch, or two consecutive attempts write no file. A failure classified as a sandbox-environment fault escalates before any model call, at zero token cost. Every such ending is an escalation, never a crash.

Per attempt, RepairAttempt.outcome ∈ {fixed, no_progress, regressed} with regression dominating: an attempt that fixes one test and breaks another is still treated as dangerous.

Escalation as a Terminal State

Each non-green ending resets the test phase to awaiting_user and sends an event of type repair.escalation with the reason field containing the reason, a short summary of the current state "here is where I am stuck", a set of failed tests, diffs already tried, the convergence metrics, and an explicit resume contract (refine the Build stage with guidance, after which repair can run again). There is no error path to escalation. This is its encoded version of the invariant always prefer escalation over silent failure, and it is how the human-control pattern defined in [21] is extended to the repair phase.

Audit Trail and Convergence Metrics

Each iteration is persisted as a RepairAttempt containing its target files, diff reference, resulting run and whether it was reverted, and the whole loop is persisted as one costed Run with outcome {fixed, escalated}. A versioned repair report captures initial_failing, final_failing, failing_by_iteration[], regressions_introduced, empty attempts, iterations, tokens_spent, cost_inr and wall_clock_s, and repair.iteration {i, failing_count, regressions, tokens} events stream to the UI while the loop runs. This report is also the unit that the evaluation harness consumes (Section VIII).

The loop's invariants are: If a diff will do, do not feed the whole repository; If the loop will not terminate, bail out; Always leave an auditable trail; Always prefer escalation to silent failure.

VI. DEPLOYMENT AND LIVE VALIDATION

[]

5.  The infrastructure analysis, dual mode credential handling, topology for deployment, and the path for live failure repair and validation after deployment. The figure shows the original Render backend; the backend now deploys to Vercel by default, with Render available as an option.

Infrastructure Analysis

An analyser will analyse the workspace; frontend build target, whether or not a persistent backend will be attached, whether or not a database will be used and what type, required environment, etc.; and produce an infra_plan artefact that identifies the project as a static frontend, or a frontend with a persistent backend, or a frontend with a backend and a database, with recommended build targets and exact environment variables and secrets each needs. The motivation given in [6] is a 30.2 % / 26.8 % first-attempt deployment success rate; deployment configuration is a failure mode beyond the scope of generation quality.

Dual-Mode Credentials and Ordered Deployment

There are two ways to deploy: Seamless, which is deployed on the provider account that hosts the platform; or Bring Your Own, which is deployed with the user's own tokens. All provider tokens are encrypted at rest using Fernet, and will only be decrypted at call time, in process, and are never logged and never returned to the client. Both tiers deploy to Vercel — the SPA as static assets and the Express backend as a function — from the same inline file upload, so no git host is involved and what ships is exactly what the repair loop validated; Render remains available for the backend as an option. Deployment is ordered: provision the database; deploy the backend with the database URI injected; deploy the frontend with the backend’s public URL injected; and health-check every node, so a dead backend never ships behind a live frontend. A pre-flight check refuses a localhost database URI before anything is deployed. The resulting topology is depicted as an interactive React Flow graph with per-node status, logs and redeploy controls.

Post-Deployment Validation

It is then re-pointed to the deployed URL with the same Playwright suite. As the live run yields the same normalised shape as in-sandbox, upon failure, the live run re-enters the same repair loop as the in-sandbox run, which is Section V: diagnose, repair, redeploy, re-validate. Live failures get at most two repair, redeploy and re-validate cycles. This closes the loop on the artifact the user will actually use, a step that none of the other system classes in Table I performs.

Notable Implementation Properties:

-   Layered configuration. More than 100 runtime settings resolve with precedence; they are admin panel > environment > default and include the repair caps and the stall thresholds; the behaviour of the loop can thus be adjusted from an administrative dashboard and tested by the evaluation harness without redeployment. At the interface, it's write-only as well, and it's encrypted at rest with Fernet encryption - the encryption key and the control-plane database URI are still in the environment, since they're read before the configuration layer exists and protect the ciphertext itself.

-   Quality gates. TypeScript is strict with ESLint and Prettier rules; the Python codebase is ruff, black and mypy clean, with full type hints and no bare exception handling. Errors are grouped into a single taxonomy that distinguishes between user and system and provider errors and provider degradation, notably design-provider quota exhaustion, is handled softly with an actionable message and a fallback, while no longer terminating the pipeline.

-   Security posture. All authorisation is enforced per route; no cross-project data access is available; generated code never runs in the control plane; the sandbox doesn't have a host network and has dropped capabilities. This is done on purpose because of the credential- and error-handling smell classes reported for AI-generated infrastructure code in [4] and the execution-environment vulnerabilities enumerated in [24] are located in the platform, not the prompt.

-   Delivery and rollback. The platform is itself delivered by a six-job CI pipeline and health-checked continuous deployment. On a k3s cluster probed every 0.2 s, a rolling update, a deliberately broken release and its automatic rollback served 807 requests with zero failures; the broken release served none.

VIII. EVALUATION

Questions and Set-up

The evaluation addresses three questions. RQ1: does the bounded repair policy improve on a no-repair baseline, and at what cost and latency? RQ2: how is the gain distributed over iterations, and is the default cap of five justified? RQ3: on whole applications, how many acceptance criteria are met, and is every failure accounted for by the system’s own explanations? All numbers come from one reproducible command (make eval), run on 2 October 2026.

Level 1 runs four industry benchmarks through ForgeFlow’s own LLM transport and repair policy: HumanEval (164 Python problems) [25]; the sanitised test split of MBPP (257) [26]; HumanEval-TS, the TypeScript translation of HumanEval from MultiPL-E (159) [27], which matches the language of the generated applications; and BFCL v3 [28] (1 000 non-live AST cases in four categories plus 240 irrelevance cases), whose function calls mirror the agents’ tool use. Level 2 runs benchmark applications through the full pipeline (requirements, build, test generation, test and repair), each in its own project, sandbox and database. All runs used one model, z-ai/glm-5.3-flash, through an OpenAI-compatible endpoint (OpenRouter) pinned to the model developer’s own upstream with fallback disabled, so every call was served by the same deployment; code generation used temperature 0 and BFCL 0.001.

Baseline and repair policy. The baseline is pass@1 on the same problems, model and grader, i.e. the no-repair arm. For each first-attempt failure, the repair arm returns the task, the current code and the last 1 500 characters of the failing output to the model — not a growing transcript — for at most five attempts, and stops after two consecutive attempts that reproduce the same failure or resubmit known code: the product defaults max_iterations = 5 and stall_threshold = 2. As in the self-repair literature [29], [30], feedback comes from the benchmark’s own tests, so the post-repair figure measures what repair adds and is not a pass@1 result. Function-level problems have no repository history, so Level 1 exercises the bounded controller but not the diff and import-graph parts of the context; those are exercised only at Level 2.

Metrics and Their Validation

Table III defines each metric and states how it was validated. Before any model output was scored, the graders were checked: 426 of 426 reference solutions (upstream references for HumanEval and MBPP plus five hand-written TypeScript controls) pass, and 580 of 580 deliberately wrong stubs are rejected. Each dataset is pinned to an upstream commit and verified by SHA-256 before use, and model-written code runs only in a container with no network, all Linux capabilities dropped, a read-only root file system and memory, CPU and process limits. The evaluation harness, including its metric pipeline, is covered by 130 unit tests. Proportions are reported with 95% Wilson score intervals [31], and paired before/after outcomes on the same problems are compared with an exact McNemar test [32].

Iteration budget. Fig. 7(b) reconstructs the outcome under smaller caps by truncating each recorded trajectory (RQ2); this is exact for the recorded run, because a cap never changes the attempts before it. Ten repairs succeeded at the first attempt and three at the second, so any cap of two or more recovers all 13 and a cap of one recovers ten. The six unrepaired problems stopped on the stall guard after two to four attempts, and none reached the cap. Without the stall guard they could have run to the cap, consuming up to 46 attempts instead of 33, at the price of not observing whether a late attempt would have succeeded. At function level the knee is therefore at one to two iterations, consistent with [9], [10]; the cap of five was never binding, and the stall guard did the bounding.

On BFCL (Table V), mean accuracy over the four AST categories was 92.7%, with a median latency of 21.5 s per case (p95 29.6 s). End-to-End Applications

The full-pipeline run was stopped after the first two of the ten specifications to stay within the evaluation budget; Table VI reports them (one run each), and we do not generalise from two applications. The test-generation agent wrote tests tagged with criterion identifiers that covered all 16 acceptance criteria. Explainability and Failure Analysis

Explainability. ForgeFlow’s explanations are its stop reasons, escalation summaries and criterion links, so we checked that every outcome is attributable to one of them. All 580 code problems ended with a recorded stop reason (561 first-attempt passes, 13 repairs, 6 stalls; no cap hits and no provider errors); all 141 BFCL failures carry a typed error; and both application escalations carry a typed reason, the failing tests and their criterion identifiers, with each of the four unmet criteria traced to specific failing end-to-end tests. This validates that the explanations are complete and traceable, not that users find them useful, which requires a user study.

Failure modes. (i) End-to-end failures fall outside the repair context; mapping a failing browser test to the pages and routes it visits is the clearest next step. (ii) Resource contention: in an isolated re-run of a third application’s end-to-end suite both of its tests passed in 2.3 s, so some end-to-end failures may come from building several applications at once on one machine rather than from the generated code. (iii) Over-eager tool use, as in the BFCL irrelevance category. (iv) Running the evaluation exposed five harness and platform defects that no unit test had caught — e.g. the test-generation agent was not wired into the pipeline, so early pass rates measured only placeholder tests, and Playwright sized its workers from the host’s CPU count and exhausted the sandbox’s process limit. Each was fixed and covered by a regression test; each would otherwise have shown up as a model or repair failure.

IX. DISCUSSION AND LIMITATIONS

Discussion

The design of ForgeFlow can be interpreted as a series of engineering assurances based on the literature search of the last year that yielded negative results. The iterative self-improvement can compromise security [5] and little improvement will happen after a few rounds [9] [10] so there is a cap and a guard on the loop. The repair context is diff-first by construction because generated tests lose validity as soon as the code changes, and the recommended mitigation is a highlighted diff [11]. The pipeline is static and the skeleton is duplicated instead of generated because elaborate agency underperforms structured pipelines at higher cost [13]. The professionals stay in control, agents move away from intent at scale [7,8] and each stage is thus skip-able, redo-able and versionable, and non-convergence escalates to a human instead of eating budget. Because generation quality does not predict deployment success [6], deployment is followed by explicit classification of infrastructure and then validation with the live artifact.

Practical meaning of the metrics. At function level the base model is near its ceiling, so the absolute pass rates say more about the model than about ForgeFlow; what the evaluation isolates is the policy, which recovered two-thirds of first-attempt failures for 5.7% more calls and ended every unproductive trajectory before the cap. At application level the meaningful unit is the acceptance criterion, not the test: both applications passed 87–89% of their tests yet met only 71–78% of their criteria and were not delivered, because the criterion metric does not let passing unit tests stand in for failing end-to-end behaviour. Making that gap visible, instead of reporting a high test pass rate, is the purpose of the criterion_id chain.

Threats to Validity

Construct. Generated-test pass rates measure agreement between generated code and generated tests, not the user’s intent; the criterion metric, and counting an untested criterion as unmet, reduce but do not remove this risk. Function-level benchmarks exercise the bounded controller, not the diff-aware context. Internal. Each configuration was run once with one model. Temperature 0 reduces but does not remove non-determinism, so the intervals reflect sampling over problems, not over runs. Application builds ran concurrently on one machine, which may have caused some end-to-end failures. HumanEval and MBPP are public and may appear in the model’s training data, inflating pass@1; this affects absolute levels more than the repair delta, and HumanEval-TS and BFCL partly mitigate it. External. Results are specific to one model, one generated-app stack and small CRUD-style applications, and should not be generalised to other stacks, large existing codebases or repository-level maintenance [12], [14]. Conclusion. With 19 first-attempt failures and two applications, effect sizes are imprecise; only the pooled function-level repair effect is statistically significant. The literature review is targeted rather than exhaustive (Section II).

Limitations

The evaluation is partial: two of the ten applications were run, once each and with one model; the application-level no-repair and context-ablated arms, repeated runs and a second model have not been run, so the value of the diff-aware context is untested and whole-application repair is unproven. The repair loop cannot yet act on end-to-end failures. The generated-app stack is fixed, which restricts applicability. Design intake inherits the visual-fidelity limits reported in [23], which is why the stage is human-refinable. Generated tests can satisfy the letter of a criterion but not its intent. The control plane runs as a single node, and the escalation summaries have not been evaluated with users. Mobile, desktop and native targets, multi-user collaboration, payments in generated applications and enterprise compliance are outside the scope.

X.  CONCLUSION AND FUTURE WORK

Generation is no longer the limiting factor in AI-powered software delivery; verification is. Five independent lines of 2025–2026 evidence point the same way: AI-generated artifacts carry systematic quality and security defects; iterative self-improvement can make code worse; generated infrastructure often fails to deploy; generated tests lose validity when code changes; and developers do not want to give up control. ForgeFlow is a working, human-in-the-loop, non-linear platform that takes an idea from screenshots or a specification to a live, validated URL, with a bounded, diff-aware, escalating repair loop at its centre. Its distinguishing commitment is a negative one: the system knows when to stop, and it returns the problem with an auditable account of what it tried. The evaluation supports this at function level, where bounded repair converted 13 of 19 failures within two attempts and stopped itself on the rest, and it exposes the current limit at application level, where browser end-to-end failures fall outside the repair context. Future work, in order of priority: map failing end-to-end tests to the pages and routes they visit so that repair can act on them; run all ten applications in the no-repair, bounded diff-aware and context-ablated arms with repeated runs and a second model, reporting convergence, cost per success and latency with variance; compare sandbox and live pass rates to quantify live validation; evaluate the escalation summaries with users; grow the corpus to 20–30 specifications; and test a learned stopping rule under a hard cap, and the transfer of the bounded controller to repository-level maintenance.
